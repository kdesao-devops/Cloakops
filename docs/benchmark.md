# Detection benchmark

Methodology in [ADR 0004](adr/0004-recall-first-benchmark.md) and
[ADR 0013](adr/0013-benchmark-implementation.md). Latest numbers: `bench/reports/latest.md`
(regenerated by `uv run python bench/run.py`, gated in CI).

## Corpora

| Corpus | Content | What its score means |
|---|---|---|
| synthetic | 10 templates x 20 seeded documents: tfstate, plan, Kubernetes, CloudTrail, nginx, JSON logs, `.env`, kubeconfig, GitHub Actions, incident note | Regression signal only: the rules were written against these formats |
| dev | Hand-written samples already used to improve the rules | Progress on realistic content, but biased by the fixes |
| holdout | Hand-written samples never used to tune anything | The only number that estimates real-world recall |

## Results history

### 2026-11-14: holdout v1 (first measurement, rules layer only, before any fix)

8 hand-written documents (Ansible inventory, ssh_config, Helm values, Python traceback, AWS CLI
output, Slack incident thread, docker-compose, tfvars), written by the author of the rules.

| Recall | Precision | Documents with a leak |
|---|---|---|
| 77.2% | 86.4% | 7 / 8 |

What it showed:

- a real rule bug: IAM unique IDs are 4 + 17 characters, the rule expected 16;
- people and organizations in prose are not caught by rules at all (expected: phase 2, NER and
  local LLM);
- usernames behind keys such as `ansible_user` or `User` (ssh_config) were missed;
- two "false positives" were annotation mistakes (an internal hostname and a key path containing
  the company name were correctly masked but not labeled).

Per ADR 0004, these documents then moved to the **dev** corpus and drove fixes; a new holdout set
is needed, ideally written by someone other than the author of the rules.

### After fixes (same day)

| Corpus | Recall | Precision | Documents with a leak | Blocked by the re-scan |
|---|---|---|---|---|
| synthetic | 93.5% | 100.0% | 20.0% | 0 |
| synthetic, no propagation | 91.9% | 100.0% | 30.0% | 22 |
| dev | 84.7% | 91.7% | 37.5% | 0 |

Readings:

- **Propagation** adds recall and, more importantly, removes all re-scan blocks: without it, a
  value detected in one place but repeated elsewhere is found in clear by the re-scan and the
  document is refused (fail-closed). Propagation is what makes fail-closed usable.
- Remaining synthetic misses are by design of the corpus: names of people and organizations in
  prose (incident note), and IAM role names behind a plain `name =` attribute.
- Remaining dev misses: prose names (phase 2), an organization in a container registry path
  (`ghcr.io/<org>/`), a public hostname of the organization not configured as an organization
  domain.
- Remaining dev false positive: a database username (`payments`) masked and propagated to the
  chart name and image path. Debatable: a username is half a credential.

### After the re-scan amendments and the organization signals (ADR 0014, ADR 0015)

Synthetic corpus extended with 4 templates (Git remotes and registry, AWS SSO config,
certificate, source header): 280 documents.

| Corpus | Recall | Precision | Leak after detection | Blocked (default) | Leak in final output |
|---|---|---|---|---|---|
| synthetic | 95.9% | 100.0% | 14.3% | 0 | 40 docs |
| synthetic, no propagation | 88.1% | 100.0% | 42.9% | 62 docs | 58 docs |
| synthetic, no propagation, `--redact` | 88.1% | 100.0% | 42.9% | 0 (62 redacted) | 80 docs |
| dev | 86.4% | 90.0% | 25.0% | 0 | 2 docs |

Readings:

- The re-scan fails closed by default; `--redact` is an explicit option (ADR 0014). Without
  propagation, the default blocks 62 documents; `--redact` sends them with `[REDACTED]` holes.
  With propagation, the re-scan has nothing left to catch on these corpora.
- What still leaks, on every corpus: **names of people and organizations in prose** (incident
  notes, chat threads), and an IAM role name behind a plain `name =` attribute. The re-scan
  cannot catch them: it only knows values detected somewhere. This is the case for phase 2
  (NER, local LLM).
- The entropy rule now rejects tokens with 9+ lowercase letters in a row (identifiers made of
  words such as `sha256WithRSAEncryption`); measured cost: 0.59% of random 40-character secrets.

### 2026-11-14: holdout v2 (first real-world data, before any fix)

Two real Terraform states provided by the project owner (Keycloak lab: realm, OIDC client,
groups, users). They are consecutive states of the same stack (serial 43 and 48), so they count
as one document twice. Annotated **before** running the tool on them, following the policy of
the ADRs: the OIDC client secret, two initial passwords (`"value": "temp"`), two usernames and
their reuse in Terraform resource addresses (11 values per file). Not annotated: Keycloak object
UUIDs, generic names (`lab`, `argocd`, `developers`), `argocd.localtest.me` (public, resolves to
127.0.0.1), the `private` fields (base64 of `null` and of `{"schema_version":"1"}`).

| | Recall | Precision | Documents with a leak |
|---|---|---|---|
| with propagation | 54.5% | 15.8% | 2 / 2 |
| without propagation | 27.3% | 100% (2 documents blocked by the re-scan) | 2 / 2 |

What it showed:

- **Precision collapses on real data, and propagation amplifies false positives exactly as it
  amplifies true positives.** One wrong detection becomes dozens of masked occurrences.
- Key-name heuristics misfire on Keycloak attribute names: `access_token_lifespan: "5m0s"`
  (token), `discoverable_credential: "required"` (credential), `reset_credentials_flow`,
  `access_code_lifespan_login` (the `*login` person suffix added after holdout v1 overreaches).
- Exact-value propagation rewrites **JSON keys**: the value `required` was propagated into
  `backchannel_logout_session_required`, `consent_required`, `ssl_required`.
- `client_id` (masked by ADR 0009 as an organization-identifying ID) catches Keycloak client
  names (`argocd`) and propagates them into URLs and scope lists.
- The entropy rule flags base64 of JSON (`eyJzY2hlbWFfdmVyc2lvbiI6IjEifQ==`).
- Misses: passwords whose key is a generic `value` inside `initial_password`; a 3-letter
  username (`bob`) is too short to be propagated, so its reuse in resource addresses leaks.

**Annotation revised by the project owner** after reading the results (ground truth, not tool
tuning): the backup state was deleted as a duplicate (one document left); the OIDC `client_id`
(`argocd`, a lab name but still the client's identity) and its UUID are sensitive, wherever they
appear; base64 content (`private`) is to be masked too, since base64 is trivially decoded. With
that annotation and still no rule change: **recall 72.2%, precision 35.1%**, 1 / 1 document
leaks. The owner also ruled that `required` (and similar enum values) can never be sensitive,
and that durations such as `5m0s` must be excluded. The document then moved to `dev`.

After the fixes (enumerated settings and durations are never values to mask; keys about a
credential's lifecycle such as `*_lifespan*`, `*_timeout`, `*_flow`, `*_reuse` are not
credentials): the Keycloak document reaches **recall 72.2%, precision 100%** (from 35.1%).
Still missed, accepted by the owner as lab test values: two `initial_password` values under a
generic `value` key, and a 3-letter username reused in resource addresses.

The dev corpus now has 9 documents (83.1% recall, 92.1% precision); the 8 previous ones are
unchanged (86.4% / 90.0%), so the ratchet was re-baselined for the new corpus, not lowered for
a regression. The holdout is empty again.

## Known limits of this benchmark

- The synthetic corpus and the rules share an author; the synthetic score is not evidence.
- The dev corpus is small (8 documents) and its score moves a lot per document.
- Recall counts characters that must be masked; generic words the pseudonymizer keeps by design
  (`prod`, `deployer`) are exempt. The keep-list is therefore part of what is evaluated.
